# Code review findings (November 2026)

Six reviewers each covered one area; a separate checker then tried to disprove every finding.
Only findings the checker confirmed are listed. Severity is the checker's. Line numbers refer to the code as of the slayer panel commit and may drift after fixes.

Evidence notes mention upstream sources that were checked: RuneLite master, Skretzo/shortest-path, weirdgloop/osrs-dps-calc `equipment.json`, runelite/plugin-hub tooling, and Slayer Sensei's data.

## Bank organizer

### [high] Variation-tagged gear is laid out and classified as the variation group's base item, which is often a broken, inactive, uncharged or Gauntlet version

- **Where:** `src/main/java/com/combatgearorganizer/CombatGearOrganizerPlugin.java`:266
- **Problem:** ::gearadd tags with variation=true (line 206). TagManager then stores the tag under -(ItemVariationMapping.map(canonical id)). collectItemIds turns that back into the group's base id (canonicalize(abs(id))), and toGearItem classifies that base id and writes it into the layout. In item_variations.json the base is simply the first id in each group, and for a lot of end-game gear that first id is not the item the player owns. Examples: Infernal cape -> 21287 INFERNAL_CAPE_BROKEN; Dizana's quiver -> 28826 DIZANAS_QUIVER_BROKEN; Bow of faerdhinen -> 25862 BOW_OF_FAERDHINEN_INACTIVE; Crystal helm -> 23886 CRYSTAL_HELM_BASIC (the Gauntlet version); Serpentine helm -> 12929 SERPENTINE_HELM_UNCHARGED; Toxic blowpipe -> 12924 TOXIC_BLOWPIPE_EMPTY; Slayer helmet (i) -> 11864 SLAYER_HELMET; Amulet of glory(4) -> 1704 AMULET_OF_GLORY. Concrete case: you wear an Infernal cape and type ::gearadd. The item is classified from the stats and name of 'Infernal cape (broken)'. The broken/inactive versions are most likely not equipable, so the cape would land in the Supplies section. While the cape is worn (not in the bank), LayoutManager draws the unmatched layout id as a layout placeholder, so the tab shows a ghost 'Infernal cape (broken)' / 'Bow of faerdhinen (inactive)' icon. Sorting by power within a slot is also based on the wrong item's stats.
- **Evidence:** TagManager.getItemId (real source): itemId = ItemVariationMapping.map(canonicalize(abs(id))) * -1. ItemVariationMapping static block: base = iterator.next(), the first id in each JSON group. item_variations.json groups checked: 'infernal cape' [21287,...], 'dizanas quiver' [28826,...], 'bow of faerdhinen' [25862,...], 'crystal helm' [23886,...], 'serpentine helm' [12929,...], 'toxic blowpipe' [12924,12926]. Ids resolved to names with runelite-api ItemID.java. LayoutManager.layout(): an unmatched layout id gives bankItemId = itemId, and drawItem then draws it as a layout placeholder when qty == 0.
- **Fix:** Don't classify or lay out the group base id. In ::gearadd, also record the actual worn ids: use canonicalize(item.getId()) for both classification and the layout entry, because LayoutManager.matchesVariant still matches other variations. For -base tags that come from getItemsForTag, pick the variation actually present in the bank, worn equipment or the existing layout, or else the variation with the best equipable stats, instead of the base.
- **Checker's note:** Confirmed. Upstream TagManager.getItemId stores variation tags under -ItemVariationMapping.map(canonical). ItemVariationMapping takes the first id of each JSON group as the base (iterator.next()). I fetched the current master item_variations.json: infernal cape starts at 21287, dizanas quiver at 28826, bow of faerdhinen at 25862, crystal helm at 23886, serpentine helm at 12929, toxic blowpipe at 12924, slayer helmet at 11864 and amulet of glory at 1704, all as the finding says. collectItemIds (line 266) converts -base back to base. toGearItem then classifies that base id with itemManager.getItemStats/getItemComposition and writes it into the layout. When the real item is in the bank, LayoutManager.matchesVariant still shows the correct item. When the item is worn, the unmatched base id goes to drawItem as a qty-0 layout placeholder, so the ghost is the wrong (broken/inactive) icon. RuneLite's own auto-add would store canonicalize(realId) instead. I could not get item stats to confirm that the broken/inactive bases are not equipable (static.runelite.net is blocked). In-game, the Bow of faerdhinen (inactive) cannot be wielded, so the Supplies misclassification is very likely for at least that item, and sorting on the wrong item's stats is certain. Severity stays high because ::gearadd is the main workflow and this hits flagship end-game items.

### [medium] An item tagged both normally and by ::gearadd gets two layout slots, one of which is a permanent ghost placeholder

- **Where:** `src/main/java/com/combatgearorganizer/CombatGearOrganizerPlugin.java`:264
- **Problem:** getItemsForTag returns both the plain key (+X) and the variation key (-base) when an item has both tags. collectItemIds adds both X and base to the set, because they are different ids. LayoutManager.layout() runs matchExact over all layout ids first, so X claims the real bank item and removes it from bankItems. When matchesVariant then runs for base, X is no longer available, so base stays unmatched and is drawn as a qty-0 layout placeholder. Common case: you tagged 'Slayer helmet (i)' (11865) by hand earlier, then wear it and type ::gearadd. -11864 is added, and ::gearsort lays out 11865 plus a ghost 'Slayer helmet' 11864 next to it. The same happens for glory(4), Ahrim's hood 100, imbued rings, defenders and other variation items. Every later ::gearsort brings the ghost back.
- **Evidence:** TagManager.getItemsForTag returns raw config keys, both positive and negative ids. LayoutManager.layout(): the matchers loop runs exact over every layout id before placeholder and variant matching, bankItems.remove(matchedId) is called after each match, and an unmatched id falls through to drawItem(..., itemId) and the 'Layout placeholder' branch.
- **Fix:** De-duplicate by variation group before building the layout. If any id in the set maps (ItemVariationMapping.map) to the same base as a -base tag, keep only the concrete ids for that group and drop the bare base.
- **Checker's note:** Confirmed against upstream TagManager.getItemsForTag, which returns raw keys, both +X and -base. In LayoutManager.layout the matchers loop runs matchExact over every layout id first and calls bankItems.remove(matchedId). The real item X is therefore taken by the exact match, matchesVariant finds nothing for base, and base is drawn through the 'Layout placeholder' (qty==0) branch. The same happens without a manual tag: if the existing layout already holds the concrete canonical id (RuneLite auto-adds canonicalize(bankItemId) for unlaid items), line 270 merges it back in next to the base id from the variation tag, which also produces the ghost. Because the existing layout is always merged back in, the ghost returns on every sort.

### [medium] Every sort throws away the user's manual layout edits with no undo, and RuneLite's AutoLayout API, which offers Keep/Undo, is not used

- **Where:** `src/main/java/com/combatgearorganizer/CombatGearOrganizerPlugin.java`:247
- **Problem:** organize() overwrites layout_<tag> without asking. It runs from ::gearsort, from the hotkey (line 97) and, by default (organizeOnAdd=true), after every ::gearadd. Any drag reordering, blank spacing or 'Duplicate-item' copies the user made are lost, and the LinkedHashSet in collectItemIds collapses intentional duplicates. One stray hotkey press or ::gearadd re-sorts a hand-tuned tab with no way back. RuneLite already provides LayoutManager.registerAutoLayout(plugin, name, AutoLayout). That puts an 'Auto layout: <name>' entry on the tab's Disable-layout menu, previews the result, and offers '1. Keep / 2. Undo'. This fits the 'better organize my tab' goal better than an irreversible overwrite.
- **Evidence:** Real LayoutManager.registerAutoLayout (public synchronized) and onMenuEntryAdded: generateLayout(old), then plugin.openTag(tag, new_), then a Keep (saveLayout) / Undo (openTag(tag, old)) chatbox menu. AutoLayout interface: Layout generateLayout(Layout previous). The README itself states that 're-running ::gearsort will reset them'.
- **Fix:** Register an AutoLayout (and unregister it on shutDown) that wraps LayoutBuilder, so the user gets the preview with Keep/Undo. At minimum, keep the previous layout string so it can be restored (for example with ::gearsort undo), and make organizeOnAdd default to false.
- **Checker's note:** Confirmed. organize() calls layoutManager.saveLayout(new Layout(tag, arrangement)) unconditionally. The LinkedHashSet collapses duplicate entries. organizeOnAdd defaults to true, so every ::gearadd re-sorts. Upstream LayoutManager has a public registerAutoLayout, and its menu offers 'Auto layout: <name>' with '1. Keep' / '2. Undo' (lines ~675-697). The plugin never uses it. One overstatement: the hotkey defaults to Keybind.NOT_SET, so a 'stray hotkey press' only applies if the user binds one. The README admits that re-running resets edits. The irreversible loss of user work is still real.

### [medium] Stale and untaggable layout entries are kept forever; 'Remove-tag' cannot remove the base ids this plugin writes

- **Where:** `src/main/java/com/combatgearorganizer/CombatGearOrganizerPlugin.java`:270
- **Problem:** collectItemIds merges every positive id from the existing layout back in and never removes any. RuneLite's own removal path, 'Remove-tag' on a laid-out tab, calls activeLayout.removeItem(itemId) with the id of the bank widget, which is the concrete variation or placeholder id. It then calls tagManager.removeTag(itemId, tag), which removes both the plain and the variation tag. Because this plugin stored the base id (finding 1), removeItem does not match it. The tag is gone but the base id stays in the layout, and the next layout pass draws it as a ghost placeholder. Every later ::gearsort keeps it and re-sorts it into a gear section. The only way to get rid of it is 'Remove-layout' on each ghost. The same applies to items untagged through 'Edit-tags', which never touches the layout.
- **Evidence:** TabInterface.java ~line 788-795 (real source): activeLayout.removeItem(itemId); layoutManager.saveLayout(activeLayout); tagManager.removeTag(itemId, activeTag). Layout.removeItem compares ids exactly (layout[i] == itemId). CombatGearOrganizerPlugin lines 269-277 add every existing layout id > 0 without filtering.
- **Fix:** When re-sorting, keep an old layout id only if it is still tagged (positive or variation key), is a concrete id whose variation group is tagged, or was added by LayoutManager for a prefix-matched item. Fixing finding 1 (storing concrete ids) also makes Remove-tag work again.
- **Checker's note:** Confirmed. In upstream TabInterface (~line 788-794), Remove-tag calls activeLayout.removeItem(e.getItemId()), which is the concrete bank widget id, then tagManager.removeTag(itemId, activeTag). Layout.removeItem compares layout[i] == itemId exactly, so a base id such as 21287 stays when 21295 is removed. Once the tag is gone the item is filtered out of bankItems, the base id goes unmatched and is drawn as a ghost. collectItemIds lines 269-277 re-add every positive existing layout id without checking whether it is still tagged, so the entry survives every ::gearsort. Untagging through Edit-tags has the same result.

### [low] Newly matched variations and prefix-matched items land unsorted at the bottom until a second sort

- **Where:** `src/main/java/com/combatgearorganizer/CombatGearOrganizerPlugin.java`:264
- **Problem:** The tab filter uses TagManager.findTag(itemId, tag), which is a prefix match (tag.startsWith(search)), and a single -base variation tag can match several bank items (for example glory(4) and glory(1), or two slayer helm colours). getItemsForTag is an exact match and produces only one layout slot per variation group. LayoutManager then appends the remaining bank items after the layout and saves them, so they sit unsorted at the end until the user runs ::gearsort again.
- **Evidence:** TagManager.findTag: tags.stream().anyMatch(tag -> tag.startsWith(Text.standardize(search))) against getItemsForTag's exact getTags(...).contains(tag). LayoutManager.layout(): the 'Items from the bank but not in the layout' loop calls addItemAfter and then saveLayout(l).
- **Fix:** When the bank is open, build the id set from the bank items that pass the same filter (tagManager tags plus each variation present in the bank), or from bankTagsService.getActiveBankTag().contains(id) over the bank container, so one pass covers everything the tab shows.
- **Checker's note:** Confirmed. Upstream buildSearchFilterBankTag filters with tagManager.findTag(itemId, tag), which uses tag.startsWith(search), while getItemsForTag uses exact contains. A single -base key produces one layout slot, but several bank variants (e.g. glory(4) and glory(1)) can match it. LayoutManager appends the extras through addItemAfter(canonicalize(id)) and saveLayout. The next ::gearsort picks them up through the existing-layout merge, so the effect is cosmetic until the user re-sorts.

**What this reviewer found solid:**
